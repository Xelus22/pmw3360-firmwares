# PMW3360 SROM 0x04 (PixArt) vs 0x05 (SteelSeries TrueMove3)

The `0x05` blob is SteelSeries' TrueMove3 firmware. It is PixArt's `0x04` plus about 560 bytes of SteelSeries code.

Both blobs come from [openinput-fw/sensor-blobs](https://github.com/openinput-fw/sensor-blobs). Everything below comes from decrypting both and comparing them instruction by instruction, together with a dump of the PMW3360's mask ROM. None of it has been measured on a sensor.

## Summary

| | 0x04 (PixArt) | 0x05 (TrueMove3) |
|---|---|---|
| `SROM_ID` reads | `0x04` | `0x05` |
| SPI registers it handles | `0x0D 0x0F 0x2C 0x2F 0x41 0x42` | same |
| Hidden extended angle snap (`0x45` → reg `0x41`) | yes | yes |
| Smoothing ≤ threshold | level 1 (2-frame average) | level 1 (2-frame average) |
| Threshold | 2000 CPI | **3500 CPI** |
| Smoothing above threshold | level 5 (32-frame average) | level 4 on 2-frame sums (**covers 32 frames**) + frame pairing |
| Smoothing with angle snap | ≥ level 6 | ≥ level 6 |
| Extra latency above threshold | none | ~1 frame (frame pairing) |
| Frame rate logic | exposure-based, ~3.4k FPS slow mode | same (code moved, unchanged) |
| Extra per-frame motion pass | no | yes (see below) |

The 3500 CPI threshold matches SteelSeries' "true 1-to-1 tracking up to 3500 CPI" claim for TrueMove3.

## Background: the smoothing filter

Both blobs use the PMW3360 mask ROM's motion filter, a **moving average over the last 2^level frames**:
- the last N raw X/Y deltas sit in a ring buffer, and running sums are kept;
- each frame outputs `sum >> level`;
- the remainder is carried into the next frame, so no counts are lost.

The SROM's job is to pick the level from the CPI setting.

| Level | Frames averaged | Delay at ~11.5k FPS |
|---|---|---|
| 0 | 1 (no smoothing) | 0 |
| 1 | 2 | ~0.04 ms |
| 4 | 16 | ~0.65 ms |
| 5 | 32 | ~1.3 ms |
| 6 | 64 | ~2.7 ms |

## Difference 1: threshold and level

| CPI | 0x04 | 0x05 |
|---|---|---|
| ≤ 2000 | 1 | 1 |
| 2100–3500 | **5** | **1** |
| > 3500 | 5 | **4** (+ frame pairing) |

So between 2100 and 3500 CPI, TrueMove3 smooths much less than PixArt's blob.

## Difference 2: frame pairing (above 3500 CPI)

Above 3500 CPI in run mode, TrueMove3 wraps the ROM filter and processes frames in pairs.

**Frame A (first of the pair):**
1. Read this frame's raw X/Y motion and store it (XRAM `0x8319` / `0x831B`). Don't filter it.
2. Output the leftover half of the previous pair's result (zero on the very first pair).

**Frame B (second of the pair):**
1. Add frame A's stored motion to this frame's motion.
2. Run the moving average once on that 2-frame sum, so the ring buffer advances once per pair.
3. Output half of the result now and keep the other half for the next frame A. The split is an arithmetic shift with the exact remainder kept, so nothing is lost.

```
frame:     A1        B1            A2           B2
raw:       a1        b1            a2           b2
filter:    -         avg(a1+b1)    -            avg(a2+b2)
output:    leftover  ½·avg(a1+b1)  ½·avg(a1+b1) ½·avg(a2+b2) ...
```

Effects:
- **Motion updates at half the frame rate**, smeared over 2 frames.
- **About 1 extra frame of delay:** frame A waits for B, and half of each result goes out a frame later.
- **Level 4 is not lighter than 0x04's level 5.** Each of its 16 buffer entries is a 2-frame sum, so the window covers 32 frames, the same span as level 5. Above 3500 CPI, TrueMove3 is therefore the same smoothing window as 0x04, plus the pairing delay.

At 3500 CPI and below, none of this runs.

## Difference 3: a second per-frame motion pass

In the frame state machine's run state, 0x05 also runs an extra routine every frame. It:
1. reads the raw motion registers (`D1 = 0x1D`);
2. calls two ROM routines (`0x0A37`, `0x088E`);
3. reprograms the sensor's resolution scaler, using either the CPI setting or a fixed value (`0x18`, 2500 CPI) depending on two internal flags;
4. writes values back into the motion registers.

This probably belongs to SteelSeries' 1-to-1 / resolution-scaling feature. What it is for hasn't been pinned down.

## Which is better?

**For the lowest latency, neither stock blob.** Use a level-0 build from this repo; all of them are based on `0x04`.

Between the two stock blobs:

| CPI range | Less smoothing / latency |
|---|---|
| ≤ 2000 | Equal |
| 2100–3500 | **0x05** (level 1 vs 5) |
| > 3500 | **0x04** (same window, no pairing delay) |
